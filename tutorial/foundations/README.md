# `foundations` — the first five examples

This is the shared project for [Example 1](../01-executable.md) through
[Example 5](../05-refined-types.md). Each example adds one Lean module, one
boundary and one binding; the Go program at `cmd/learn` calls all of them.

The point is the loop, repeated five times:

```
edit lean/LeanPort/<Module>/*.lean
edit leanport.toml
leanport check
leanport build
go test ./...
```

## Layout

```
foundations/
├── go.mod
├── leanport.toml                       # one contract, ten exports
├── lean/
│   ├── lean-toolchain                  # leanprover/lean4:4.29.1
│   ├── lakefile.toml
│   ├── Main.lean                       # Example 1 as an executable
│   └── LeanPort/
│       ├── Basics/                     # Example 1: executable code
│       ├── Functional/                 # Example 2: pure functions, recursion
│       ├── Division/                   # Example 3: specifications and proofs
│       ├── Wallet/                     # Example 4: a business invariant
│       └── Refined/                    # Example 5: types carry invariants
├── internal/verified/learn/            # GENERATED by `leanport build`
└── cmd/learn/
    ├── main.go                         # calls every example from Go
    └── main_test.go
```

All ten exports share one generated Go package, `learn`. That is deliberate:
it keeps the examples in one build and one Go import. In a real project you
would usually give each domain its own package, as `permctl` does with `authz`.

## Run it

```bash
cd tutorial/foundations
leanport check
leanport build
go test ./...
go run ./cmd/learn
```

`leanport build` produces a runtime-linked archive (about 29 MB) because the
later examples use `Nat`, `Option` and `Fin`. The archive is not committed; the
generated Go source is. After a fresh clone, run `leanport build` once before
`go test`.

Expected output:

```text
increment 41 = 42
sumTo 4 = 10
isEven 7 = false
quadruple 3 = 12
safeDivide 12 3 = 4
safeDivide 12 0 = 0
allowed(100, 30, 2) = true
balanceAfter(100, 30, 2) = 68
allowed(100, 99, 2) = false
balanceAfter(100, 99, 2) = 100
checkedDivide 10 2 = 5
checkedDivide 10 0 = 0
percent 42 = 42
percent 250 = 100
slot 10 20 30 1 = 20
slot 10 20 30 99 = 10
```

## Why one package is runtime-linked

LeanPort chooses a boundary mode per generated Go package. A scalar-only export
can use a runtime-free archive (tens of kilobytes). A package that uses `Nat`,
`Option`, `Fin`, `String` or `ByteArray` needs the Lean runtime and becomes
runtime-linked (tens of megabytes). Because all five examples share `learn`,
one example's runtime requirement selects linked mode for the package.

Example 6, `permctl`, keeps every value scalar and gets a ~27 KB runtime-free
archive. That is the trade-off, not a different tool.
